## 必须处理的接入问题

1. **P1，正式装配缺失**：M02 controller 要求 req.identity，当前 M01 在路由中通过 IdentityService.session() 鉴权，并非同样的请求中间件。需接入真实身份、CSRF、统一幂等执行器、SqlTx；否则只有模块文件，不会产生可用业务接口。
2. **P1，外部端口未交付**：当日饮水调用 M05 PointsPort；看板和大屏调用 M03/M04/M05/M06 查询端口。不得把空数据或测试积分当成真实模块。接入真实端口后验证同事务奖励和一致性快照。
3. **P1，M01 业务错误被转成 500**：交付 `http.ts` 的 catch 只识别 HealthError 或 VALIDATION_ERROR。直接注入会抛 ApiFailure 的 M01 幂等执行器后，409 幂等冲突等会被错误映射成 INTERNAL_ERROR。需在适配层明确转换已知 M01 业务错误，并补回归测试；不能放开任意对象的 status/message。
4. **P2，前端测试仍主要覆盖旧演示模型**：本次通过的 20 项交付单元测试不能证明真实 MySQL/身份/积分链路正确。交付手册的 11 组 MySQL 验收属于对方记录，本次没有复跑，不能作为本次已验证结论。
5. **P2，双仓库构建路径**：后端采用 NodeNext，需要 `.js` 导入及调整共享类型相对路径；前端应保留现有 server 排除设置和 API rewrite，不能直接覆盖交付根配置。

## 数据库涉及范围

M02 只写三张表，已存在于统一 V001，**不新增表、不新增 M02 迁移、不重新执行 V001、不合并队友本地数据库数据**。

| 表 | 主要字段 | 关键约束 |
| --- | --- | --- |
| health_profiles | user_id、height_cm、birth_year、target_weight_kg、water_target_ml、calorie_target_kcal、三大营养目标、goal_type、version | 每用户唯一；版本乐观锁；身高/体重/目标范围 CHECK |
| water_records | user_id、amount_ml、recorded_at、business_date、timezone、source、deleted_at | 单次 1–1000ml；业务日期为 UTC+8；按用户/日期/软删除/时间/id 索引；每日6000ml由事务业务校验 |
| weight_records | user_id、weight_kg、recorded_at、business_date、timezone、source、deleted_at | 20–350kg；相同业务日期与软删除规则；时间和id稳定排序 |

三表 user_id 均外键关联 users.id，均有创建/更新时间。档案无软删除，饮水和体重为软删除。

交付与当前后端 V001 SHA-256 完全相同：`64ec33a66c813321d12a7bbc29eff4d3981d6d3f3eacf6fc1eb7f9265efd3c56`。因此三表 DDL 一致。未连接线上数据库，不能据此声称线上已经建表。结构参考见同目录 `M02_三表结构参考_勿重复执行.sql`；线上安装/升级仍用统一 `server/db/releases/` 脚本。

| 方法 | 路径 | 功能 |
