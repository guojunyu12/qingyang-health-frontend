## 3. 阻塞问题

### F1 · P1：全量 API 代理会接管已有接口，并丢弃 M01 登录凭证

位置：[前端 proxy.ts 第 11 行](https://github.com/guojunyu12/qingyang-health-frontend/blob/69c385cb551cc1afba4be989f1b518e1f76eb1d2/src/m05/lib/proxy.ts#L11)，由 [API catch-all 第 3 行](https://github.com/guojunyu12/qingyang-health-frontend/blob/69c385cb551cc1afba4be989f1b518e1f76eb1d2/src/app/api/%5B...path%5D/route.ts#L3) 接入。管理后台存在相同代理实现。

新增 `/api/[...path]` 将所有路径发往 M05 API，且只转发 `m05_h5_session`/`m05_admin_session`，响应也只保留对应 Cookie。当前项目使用 `qy_access`、`qy_refresh`。接入该路由后，现有认证、健康、营养等 API 不再按当前统一入口工作；已有登录态不能用于 M05。

验证：直接调用 PR 的代理函数，构造携带两个 M01 Cookie 的 `/api/v1/auth/session` 请求，使用模拟上游记录转发。结果为：

```json
{"upstream":{"url":"http://127.0.0.1:3100/api/v1/auth/session","cookie":null},"status":404,"forwardedSetCookie":null}
```

其中 404 为模拟上游设定，证明的是转发目标与凭证过滤行为，不是声称进行了真实服务端到端登录测试。

修正：沿用 M01 统一 API 入口和会话机制；如保留独立代理，必须限定 M05 路径并接入同一认证适配，保留现有接口路由和 Cookie/CSRF 行为。不能直接采用 PR 的全路径代理替换当前入口。

### F2 · P1：增量迁移无法在当前数据库运行

位置：[phase6-migrate.mjs 第 8 行](https://github.com/guojunyu12/qingyang-health-backend/blob/8efef01aa9bfa9b5091893b4a4fdaedea0f92cca/db/m05/phase6-migrate.mjs#L8)；同类问题见 [application.ts 第 68 行](https://github.com/guojunyu12/qingyang-health-backend/blob/8efef01aa9bfa9b5091893b4a4fdaedea0f92cca/src/m05/application.ts#L68)。

PR 读取和写入 `schema_migrations.checksum_sha256`，当前 M01 迁移历史使用 `schema_migrations.sha256`。因此 db:m05 会在执行增量 DDL 前失败，健康检查和契约查询也不能通过。

验证：对现有测试库执行只读 `SHOW COLUMNS`，列为 `version, sha256, applied_at`；执行 PR 中的 SELECT 得到 `ER_BAD_FIELD_ERROR: Unknown column 'checksum_sha256' in 'field list'`。未运行来稿 DDL。

修正：使用现有迁移器与历史字段，对当前 V004 基线生成统一编号的增量迁移。保留已有 V001–V004 及校验值，不新建第二套迁移历史。PR SQL 已说明编号由 M01 分配，这一点应在整合时真正完成。

### F3 · P1：正式启动入口没有接入 M01 身份，真实用户和管理员无法使用

位置：[application.ts 第 49 行](https://github.com/guojunyu12/qingyang-health-backend/blob/8efef01aa9bfa9b5091893b4a4fdaedea0f92cca/src/m05/application.ts#L49)、[identity.ts 第 68 行](https://github.com/guojunyu12/qingyang-health-backend/blob/8efef01aa9bfa9b5091893b4a4fdaedea0f92cca/src/m05/common/identity.ts#L68)、[h5-main.ts 第 4 行](https://github.com/guojunyu12/qingyang-health-backend/blob/8efef01aa9bfa9b5091893b4a4fdaedea0f92cca/src/m05/h5-main.ts#L4)。admin-main 同样未注入适配器。

关闭开发身份后，两个正式入口均调用 `createApplication(config)`，最终选择 `UnconfiguredM01Identity`，其 resolve 固定返回 401 `IDENTITY_NOT_CONFIGURED`。因此开发测试账号能操作不代表真实邮箱登录用户、真实管理员能使用。该项与 F1 分开：即便代理正确转发，后端仍无可用身份适配。

修正：将模块接入 M01 认证和角色授权，使用真实邮箱会话及管理员角色；生产入口注入正式适配并在未配置时明确阻止发布。开发身份只保留于隔离测试环境。

### F4 · P1：新增事件消费者与现有 Outbox 分发器争抢事件，通知可能不执行

位置：[event-queue.ts 第 8 行](https://github.com/guojunyu12/qingyang-health-backend/blob/8efef01aa9bfa9b5091893b4a4fdaedea0f92cca/src/m05/common/event-queue.ts#L8)、[notifications/worker.ts 第 12 行](https://github.com/guojunyu12/qingyang-health-backend/blob/8efef01aa9bfa9b5091893b4a4fdaedea0f92cca/src/m05/modules/notifications/worker.ts#L12)。

M05 直接从共享 outbox_events 领取 pending 事件，完成后标记 published。当前 M01 dispatcher 同样领取该表所有 pending 事件，投递 BullMQ 后便标记 published。两者共享状态但消费协议不同。

在共享数据库并同时保留已有 Worker 的整合部署中，若 M01 先领取预约确认或权益结果等事件，M05 消费者随后不会再领取 published 行；当前统一 Worker 又没有这些 M05 的 BullMQ 消费者，通知链路将停在队列中。文件验证事件还涉及两套消费者的归属冲突。该问题依据双方领取/确认逻辑推导，未在现有业务库制造竞争。

修正：由统一 Outbox dispatcher 投递，在现有队列体系注册 M05 消费者；或由主导整合者明确唯一分发和消费归属。不得同时启用两套争抢同一状态的 dispatcher。补充双方 Worker 同时启动时的投递、重试和去重测试。

### F5 · P1：积分实现尚未向已有模块注册共享端口，无法完成饮食/健康积分闭环

位置：[application.ts 第 41 行](https://github.com/guojunyu12/qingyang-health-backend/blob/8efef01aa9bfa9b5091893b4a4fdaedea0f92cca/src/m05/application.ts#L41) 至模块装配处。

M05 创建自己的 Database、MysqlUnitOfWork、Idempotency，并通过本地控制器调用积分服务。当前项目跨模块通过 `server/src/common/ports.ts` 的 `modulePorts.points`、`pointsQuery` 等访问积分；来稿没有将积分实现注册到现有运行时，也没有接入同一事务边界。

因此仅启动这份独立 API 不会修复当前 M03 记录饮食时积分端口不可用的问题；M02 健康行为也不会自动使用这套积分规则。不能据此将跨模块积分标为完成。

修正：提供并注册共享 PointsPort/PointsQueryPort 适配，复用现有事务上下文，保持业务记录、积分、幂等及 Outbox 的原子性。验证同一请求重试、事务回滚和账号隔离。

## 4. 技术栈与数据库评估

后端来稿使用 Nest 11、TypeScript 5.9、CommonJS；当前整合项目使用 Nest 12、NodeNext/ESM。两边均为 MySQL 技术路线，但不能整体替换 package.json、tsconfig 或启动入口。需把 M05 领域实现适配到已有后端，保留现有邮件、Redis/BullMQ、上传、M02/M03 和测试依赖。

H5 的主要 Next/React 版本与当前一致；管理后台可独立建设，但仍须统一正式认证与后端契约。其开发端口 3002 与当前业务 API 3002 冲突，联调配置需调整。

来稿增量 SQL 新建 `m05_message_campaigns`、`m05_message_recipients` 两张表，并修改 notifications 的类型 CHECK，增加 `operations_message`。其他积分、活动、社区、权益数据主要使用 V001 已有业务表。整合时还需同步 M01 通知枚举、跳转白名单和读取接口，避免数据库允许但应用端拒绝的通知类型。
